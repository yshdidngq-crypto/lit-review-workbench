# 07 · 研究现状、研究方向与关联

> 三个脚本撑起两个新模块：
> `landscape.py`（本库现状）→ `directions.json`（你写的方向树）→ `link.py`（双向关联）。
> 顺序不能颠倒：现状报告给出"哪里薄"，方向树回答"薄的地方能不能做"，关联给出"外部有没有人做过"。

---

## 1. `landscape.py` —— 研究现状报告（8 问）

```bash
python scripts/landscape.py <项目目录>
```

只读 `data/papers.json` + `config.json`，输出 `data/landscape.json`。

八问固定为 **Q1–Q8，编号必须连续**（V4.2 删掉了原 Q6「怎么证明有效」与原 Q9「已经形成的共识」，
剩下的顺延重排，不留空号 —— 留空号会让 `validate.js` 的「现状报告」项判 ✗）：

| # | 问题 | 算什么 |
|---|---|---|
| Q1 | 这批文献在研究什么 | 主题构成与占比 |
| Q2 | 集中在哪些技术环节 | 每个 stage 的篇数与薄弱判断（≤max(2, 8%) 记为薄） |
| Q3 | 时间上的变化 | 逐年篇数、近三年占比 |
| Q4 | 方法派别的分布 | 方法类型构成 + 主题×方法交叉矩阵 |
| Q5 | 数据集可视化分析 | 数据集频次 + **每个数据集对应哪几篇** + 开源代码清单 + 未报告清单 |
| Q6 | 论文发表分布 | 来源数与集中度 |
| Q7 | 集中发表单位 | 单位数与集中度 |
| Q8 | 论文质量标记分布 | 饼图：无开源代码 / 未报告数据集 / 未报告指标 / 数据异常 / 置信度低 |

**Q8 是互斥分类**：一篇论文可能同时有多种问题，但饼图总和必须等于总篇数，
所以只按「最重的一类」归入，顺序为 数据异常 > 置信度低 > 未报告数据集 > 未报告指标 > 无开源代码。
扇区按篇数从大到小排，颜色按严重度定。

**Q5 的「公开」标记由作者声明**，脚本不猜：在 `config.json` 里写
`"publicDatasets": ["TNO", "M3FD", ...]`。没写这一项就不显示标记，而不是默认全部公开。

删掉的两问为什么删：Q6（指标口径分散）对"该读哪篇、能不能复现"没有决策价值，
指标数据已并入 Q8 的「未报告指标」一类；Q9（共识组合）回答的是"哪组数据集+指标被反复用"，
但数据集已由 Q5 讲清楚，单独一页没人拿它做决定。

**每条答案必须带 `caveat`。** 这不是礼貌用语，是防止误读的机制。四类固定口径写在 `boundary` 里：

- 所有比例的分母都是本批文献数，不代表学科总量
- 某主题篇数少只说明检索没覆盖到，**不能当作学术空白**
- 未报告 ≠ 没有：字段为空表示原文没给，不代表不使用
- 被引数、影响因子不参与任何判断

### 集中度为什么不能只看 HHI

HHI 的绝对值不可直接定性：17 个来源、前 5 个占一半时 HHI 只有 0.076，单看数值像"高度分散"，
但相对完全均匀（1/17≈0.059）其实已经偏高。所以脚本用 `HHI × 来源数` 归一化后再定性：
≤1.3 接近均匀 / ≤2.0 中度分散 / ≤4.0 较为集中 / 更高为高度集中。

写报告时如果直接抄 HHI 数字做判断，就会写出「前五名占一半，高度分散」这种自相矛盾的句子。

## 2. `data/directions.json` —— 方向树（这份要你自己写）

结构：一级主题 3–6 个，每个一级下 1–4 个子方向，**优先展示 6–10 个**。
用平铺数组 + `parentId` 表达层级（比嵌套好校验、好排序）。

必填字段（`link.py` 会逐项检查，缺一项就报错不写回）：

```json
{
  "id": "D1-1",
  "level": 2,
  "parentId": "D1",
  "name": "建筑层线约束下的几何解验证",
  "oneLine": "用建筑自身的横竖结构当标尺，反推变换是否可信。",
  "problem": "要解决的具体问题，2–4 句，必须指出别人的做法为什么不够",
  "whyOpportunity": "为什么这可能是机会。必须能回答：本库为什么没解决、外部是否已有人做",
  "keywords": ["facade line", "vanishing point", "楼层线"],
  "techRoute": ["第一步…", "第二步…", "…"],
  "minExperiment": "最小可验证实验：用什么数据、跑多少组、看哪一个指标就能判断方向是否成立",
  "expectedOutput": "做完能得到什么，能不能写进论文的某一节",
  "novelty": 76,
  "maturity": 28,
  "risk": 42,
  "localPaperIds": ["E230", "E108"],
  "status": "candidate"
}
```

写的时候守三条：

1. **`problem` 要能证伪。** 「提升鲁棒性」不是问题，「窗户阵列会让整层平移错一格，而残差看不出来」才是。
2. **`whyOpportunity` 不许拿"本库没有"当理由。** 本库只有 24 篇，没有某个主题只能说明你没收，
   必须先跑 `discover.py` 看外部有没有人做，再写这一段。
3. **`minExperiment` 必须小到能一个人一周内做完。** 写不出最小实验的方向，说明它还只是个愿望。

`keywords` 会被 `link.py` 用来和外部文献做匹配，**至少给 3 个英文关键词**，
否则中文方向名和英文文献匹配不上，外部关联会全空。

## 3. `link.py` —— 双向关联与派生指标

```bash
python scripts/link.py <项目目录> [--min-overlap 3] [--strict]
```

它做四件事：

**（1）结构校验** —— 必填字段、id 唯一、`parentId` 存在、`level` 与父节点匹配、
`localPaperIds` 指向真实论文、DOI 格式合法（`10.xxxx/...`）。
有任何错误就**不写回文件**，列出全部问题让人改。DOI 只允许来自检索结果原始字段，不许手写。

**（2）本库支撑度** —— 统计每个方向在本批文献里有多少篇支撑。
父方向取自己与全部子方向的**并集**，否则会出现"子方向 3 篇、父方向 2 篇"的口径倒挂。

**（3）双向关联** —— 用术语重合把外部文献挂到方向上，两侧同时写：

```
external.json[].directionIds        → ["D3","D1"]
external.json[].directionMatch      → [{directionId, overlap, sharedTerms}]
directions.json[].externalEvidence  → {count, recommendedExternalIds, fromChildren}
```

三条设计约束，都是被真实数据打出来的：

- **方向的身份只由「名称 + 一句话 + 关键词」决定。** 把 `problem`/`whyOpportunity` 也算进去，
  几百字的论证散文里必然反复出现 registration/facade/fusion，会让每个方向命中几乎所有文献
  （实测父方向一次挂上 18 篇）。
- **父方向不参与词面匹配，只聚合子方向。** 父方向是容器，让它自己匹配必然和子方向的口径打架。
- **一篇文献最多挂 3 个方向，且命中数不到最佳一半的丢掉。** 否则一篇综述会同时挂六七个方向，
  看起来处处相关，实际等于没关联。

**（4）机会分** ——

```
机会分 = 0.40×创新潜力 + 0.30×(100−成熟度) + 0.30×(100×[1−拥挤度])
拥挤度 = min(1, 外部命中篇数 / 8)
```

权重写死在脚本里，是为了同一份数据每次重算得到同一个数。页面上的排序可以换维度，
但**机会分本身不做"综合排名"用**——换个权重排序就会变。

注意 `拥挤度` 只数**外部命中的篇数**，跟本库有几篇支撑无关。页面上必须写成"外部拥挤度"：
紧挨着"本库支撑 2 篇"放一个"拥挤度 0%"，读者会以为这两个数打架，其实它们在说两件事
（一件是"我读过多少"，一件是"外面已经有多少人做过"）。

还会给每个方向写一句 `riskNote`：

| 情况 | 提示 |
|---|---|
| 本库 0 篇、外部 0 篇 | 可能是做不出来，而不是没人想到；先确认可行性 |
| 本库 0 篇、外部 >0 篇 | 可行，属于补齐型方向 |
| 本库 >0 篇、外部 0 篇 | 可能是检索词没覆盖，不宜直接判为空白 |

## 4. 顺序与依赖

```
papers.json ──landscape.py──> landscape.json ─┐
                                              ├─> build.py ──> HTML
directions.json（你写）──link.py──> 回写两个文件 ─┤
external.json（discover.py 产生）──┘
```

- `discover.py` 必须在 `link.py` **之前**跑（`link.py` 要给外部文献挂方向）
- 改了 `directions.json` 之后必须重跑 `link.py`，否则两侧关联会不一致
- 全部跑完再 `build.py`，最后 `validate.js`

## 5. 页面上的四个视觉通道不能混用

方向树的四个编码各管一件事，改配色或加新通道前先想清楚它回答什么问题：

| 通道 | 编码 | 回答 |
|---|---|---|
| 枝粗 | 机会分 | 值得投入多少 |
| 枝色 | 创新潜力 | 新不新 |
| 节点高 | 本库支撑篇数 | 有没有底子 |
| 边框 | 风险 | 会不会做不出来 |

叶子节点再多也不要换成散点图：散点丢掉父子包含关系，而方向天然是树。

**图例不写在图下。** V4.6.1 起 `chartBox` 的图下灰字（caption）一律不写（见 `02_视觉规范.md` 铁律 19），
图例复述、阈值复述、"右下象限先读"都算旁白。四个通道的含义放进卡片标题的 hint 里，
色阶阈值直接写进标题或该页的说明卡，不要挂在图下面——一图两套说法会让读者对着两行字比对。
